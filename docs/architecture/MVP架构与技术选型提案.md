# StudyPilot 第一阶段 MVP 架构与技术选型提案

## 1. 文档状态与结论

- 文档性质：`提案`，不是已经生效的架构决定。
- 对应任务：`TASK-001`。
- 适用范围：第一阶段 MVP，即资料管理与学习过程管理闭环。
- 比较基线：`e1a77bf`。
- 调研访问日期：2026-09-01。
- 生效条件：独立只读复审、阶段验收通过，并由用户决定合并到 `main` 后，才成为后续开发基线。

### 1.1 单一推荐方案

推荐采用：**Python 模块化单体后端 + REST API + React/TypeScript 单页前端 + SQLite + 本地文件存储**。

具体组成如下：

| 边界 | 推荐技术 | 解决的实际问题 |
| --- | --- | --- |
| 后端 Web/API | Python 3.13、FastAPI、Uvicorn | 用 Python 提供清晰的 HTTP 接口，并自动生成便于学习、调试和展示的 API 文档 |
| 数据访问 | SQLAlchemy 2.x | 用 Python 对象表达关系数据，同时保留以后从 SQLite 迁移到其他关系数据库的可能 |
| 数据库变更 | Alembic | 记录数据库结构如何逐步变化，避免靠手工改表导致不同开发环境不一致 |
| 数据库 | SQLite | 第一阶段是本地、单用户应用，无需额外安装和维护数据库服务 |
| 原始文件 | 本机受控数据目录 | 保留用户上传的 PDF、Word、Markdown 和 TXT 原件，数据库只保存受控路径和元数据 |
| 前端 | React、TypeScript、Vite、React Router | 用可复用界面组件承载资料库、详情、学习记录和统计等多页面交互 |
| 前端依赖 | npm + `package-lock.json` | 让其他机器可安装同一组前端依赖版本 |
| 后端依赖 | uv + `pyproject.toml` + `uv.lock` | 统一 Python 版本、虚拟环境、依赖和执行命令 |
| API 形式 | `/api/v1` 下的 REST/JSON；文件上传使用 `multipart/form-data` | 让前端、后续 AI/RAG 能力和自动化测试共享稳定边界 |
| 后端测试 | pytest + FastAPI TestClient + 临时 SQLite | 快速验证业务规则、数据库行为和 API 响应 |
| 前端测试 | Vitest + React Testing Library | 按用户看到和操作的方式验证组件，而不是只测内部实现 |
| 完整流程测试 | Playwright，首轮只覆盖关键闭环 | 模拟用户从添加资料到复习统计的真实浏览器操作 |
| 本地运行 | 开发时前后端两个进程，仅绑定本机；演示构建由 FastAPI 提供前端静态文件 | 开发时保留快速刷新，演示时可以从一个本地地址打开完整应用 |

这里的“模块化单体”是指：应用先作为一个整体部署和运行，但代码内部按职责拆成多个模块。它比“一份文件写完所有功能”更清晰，也比一开始拆成多个独立服务更适合个人 MVP。

## 2. 从已确认需求得到的架构约束

架构必须服务于 [项目需求说明](../../项目需求说明.md)和[项目背景与介绍](../../项目背景与介绍.md)，而不能反过来增加产品范围。

| 已确认约束 | 对架构的直接影响 |
| --- | --- |
| 个人使用优先 | 第一阶段按单用户、本地运行设计；不增加注册、组织、权限、支付和团队协作 |
| Python/API 学习目标 | 业务规则和 API 主要使用 Python；保留独立 HTTP API，便于理解前后端边界 |
| 第一阶段必须形成完整闭环 | 技术方案必须同时支持资料、分类、状态、进度、笔记、记录、复习和统计，不能只做上传或列表演示 |
| 先管理，后智能 | 第一阶段不实现解析、AI、RAG 或 Agent；只留下受控扩展接口 |
| 原始文件必须保留 | 文件内容放在本地受控目录，数据库保存文件元数据、校验值和内部标识；解析失败不得影响原件 |
| 删除前必须确认 | 界面确认和后端确认缺一不可；删除必须由资料应用服务统一编排，不能让界面直接删除磁盘文件 |
| 状态与进度都要保留变化过程 | 每次重要状态或进度变化要追加学习记录，不能只覆盖资料表上的最后一个值 |
| 隐私与 API Key 安全 | 原始文件、笔记和密钥不进入 Git；日志不得打印正文、笔记或完整密钥 |
| 作品展示价值 | API 文档、清晰模块边界、自动测试和可说明的数据模型都应成为项目的一部分 |
| 未来可能扩展 | 数据访问、文件存储、AI、解析和检索通过边界隔离，但当前不建设微服务或云基础设施 |

## 3. 两套可行方案的公平比较

两套方案使用相同的产品范围、SQLite、本地文件存储和安全底线。比较的是实现组织方式，不通过给某一方案附加额外需求来制造优势。

### 3.1 方案 A：FastAPI + React/TypeScript 的前后端分离模块化单体

组成：FastAPI、SQLAlchemy、Alembic、SQLite、本地文件目录、React、TypeScript、Vite。

“前后端分离”指浏览器界面与 Python 后端通过 HTTP API 交换数据。它们仍放在同一个 Git 仓库，并可作为同一个本地应用交付，不等于拆成多个微服务。

优点：

- FastAPI 基于 OpenAPI，可以生成交互式 API 文档，直接支持项目发起者的 API 学习目标；[FastAPI 官方功能说明](https://fastapi.tiangolo.com/features/)说明其以 OpenAPI 和 JSON Schema 为基础并自带交互式文档。
- React 把界面拆成组件，适合复用资料卡片、筛选器、状态控件和确认对话框；[React 官方文档](https://react.dev/)将组件描述为可组合的界面单元。
- API 是清晰的跨模块边界，后续内容解析、AI、RAG 和受控 Agent 可以复用应用服务，而不直接读取界面状态或数据库表。
- 前后端、接口和完整用户流程能分层测试，展示价值较强。

代价：

- 初学者需要同时学习 Python、HTTP、TypeScript、React 和浏览器安全边界。
- 开发时有前后端两个进程，并需要处理严格限定来源的 CORS。CORS 是浏览器允许一个地址的前端访问另一个地址后端的规则；[FastAPI CORS 官方说明](https://fastapi.tiangolo.com/tutorial/cors/)建议明确列出允许来源。
- 同一个功能通常涉及 API 契约和界面调用，若契约没有先冻结，多 Agent 并行容易产生理解不一致。

### 3.2 方案 B：Django + 服务端模板的一体化模块化单体

组成：Django、Django ORM 与迁移、Django Template Language、少量原生 JavaScript、SQLite、本地文件目录。

“服务端模板”指 Python 服务器把数据填入 HTML 模板后直接返回完整页面，浏览器不需要为每个页面维护一套独立 API 状态。

优点：

- Django 同时提供数据模型、表单、模板、迁移和测试能力，初始集成点更少，通常能更快做出 CRUD 页面。
- [Django 模型官方文档](https://docs.djangoproject.com/en/6.0/topics/db/models/)说明模型是数据的主要信息来源并提供自动数据库访问 API；[Django 模板官方文档](https://docs.djangoproject.com/en/6.0/ref/templates/)强调展示逻辑与应用逻辑分离。
- 表单验证、服务端渲染和文件管理更集中，适合尽快交付个人工具。
- 只学习少量前端 JavaScript 也能完成多数第一阶段操作。

代价：

- 独立 API 不再是产品结构的中心；若为了 API 学习再增加一套完整 API，Django 的低复杂度优势会被削弱。
- 复杂筛选、局部刷新、进度编辑和仪表盘交互逐渐增加时，需要继续加入前端约定，或者后来再迁移到独立前端。
- 后续 AI/RAG 虽然仍可在 Python 中实现，但若其他界面或 Agent 需要复用能力，必须额外建立清晰的服务/API 边界。

### 3.3 同一维度评分

评分使用 1 至 5 分，5 分表示更符合 StudyPilot 当前目标。权重在评分前按已确认项目目标设定，防止看到结果后随意调整：API 学习与作品展示占 20%，需求适配与未来扩展各占 15%，其余各占 10%。分数是针对本项目的判断，不代表技术本身的高低。

| 比较维度 | 权重 | 方案 A：FastAPI + React | 方案 B：Django 模板 | 判断依据 |
| --- | ---: | ---: | ---: | --- |
| 初始学习成本 | 10% | 2 | 4 | A 同时引入 HTTP API 与现代前端；B 初始概念更集中 |
| 第一版开发复杂度 | 10% | 3 | 5 | B 内置模型、表单、模板与迁移；A 需要维护接口和前端状态 |
| 第一阶段需求适配 | 15% | 5 | 4 | 两者都能完成；A 更适合资料筛选、进度编辑、统计等富交互 |
| 测试难度 | 10% | 4 | 4 | A 分层更清楚但工具更多；B 测试工具统一但前后行为更耦合 |
| 本地运行便利 | 10% | 4 | 5 | A 开发时两个进程，演示构建后可一个地址；B 天然一个进程 |
| 作品展示与 API 学习 | 20% | 5 | 3 | A 可展示 OpenAPI、独立契约和前后端协作，更贴合已确认学习路线 |
| 后续解析、AI、RAG、Agent 扩展 | 15% | 5 | 4 | 两者都使用 Python；A 已有显式 API/应用服务边界 |
| 当前避免过度设计 | 10% | 4 | 5 | A 必须严守模块化单体和少依赖；B 默认更精简 |
| 加权总分 | 100% | **4.20 / 5** | **4.10 / 5** | B 的快速交付优势真实存在；A 因本项目特有的 API 学习与扩展目标略胜 |

### 3.4 为什么最终选择方案 A

如果目标只是尽快做出本地 CRUD 工具，方案 B 是更稳妥的选择，它在学习成本、开发复杂度和本地运行三项中也明显领先。但 StudyPilot 同时承担“用真实项目学习 Python 后端与 API”和“形成可讲述作品”的明确目标。方案 A 增加的复杂度恰好对应要学习的真实边界，而不是为展示无关技术增加复杂度。

因此最终推荐方案 A，同时施加四个限制来控制风险：

1. 后端保持一个模块化单体，不拆微服务。
2. 前端不引入 Redux、GraphQL、大型 UI 框架或微前端。
3. 第一阶段只使用 SQLite 和本地文件目录，不选择云平台。
4. API 契约和概念模型先确定，再允许多个实现 Agent 并行。

未选方案 B 不是因为它不能满足需求，而是它会弱化独立 API 在学习路线和未来复用中的中心位置。

### 3.5 重新评估条件

只有出现下列事实之一，才重新评估本提案；不能因为出现新潮技术就更换：

- 用户确认无法承担 React/TypeScript 的学习成本，且“尽快可用”优先级明确高于 API 学习；此时重新考虑 Django 模板方案。
- 应用需要多人或多设备并发写入、远程共享或长期在线运行；此时重新评估 PostgreSQL、身份认证与部署方案。
- 原始文件超过单机磁盘管理能力，或需要跨设备同步；此时重新评估对象存储。
- 内容解析或 AI 任务需要长时间运行、失败重试和任务队列；此时才评估后台任务进程。
- 经过实际性能测量证明当前边界成为瓶颈；在没有测量证据前不拆微服务。

任何重新评估都要形成独立任务和架构决策记录，不能由功能 Agent 顺便更换技术。

## 4. 推荐系统结构

```text
用户浏览器
  │
  │ HTTP：JSON / multipart 文件 / 文件下载
  ▼
React + TypeScript 界面层
  │
  │ 只调用 /api/v1，不直接接触数据库或磁盘路径
  ▼
FastAPI 接口层
  │
  ▼
应用服务层：编排一次完整用例与事务
  │
  ├── 资料与分类模块
  ├── 学习状态与记录模块
  ├── 笔记模块
  ├── 复习模块
  └── 统计查询模块
  │
  ▼
基础设施适配层
  ├── SQLAlchemy → SQLite
  └── 文件存储接口 → 本机受控数据目录

未来扩展端口（第一阶段不实现）：正文解析、AI、RAG、学习 Agent
```

依赖方向只能由上向下。界面层不能导入数据库模型；业务模块不能导入 React 或 FastAPI；统计模块只读取已批准的数据，不反向修改学习记录。

### 4.1 为什么采用模块化单体

- “单体”解决个人项目运行和调试简单的问题：只有一个 Python 应用和一个数据库。
- “模块化”解决职责混乱的问题：资料、笔记、复习等仍有清晰所有者。
- 后续若某类长任务确实需要独立进程，可以从已经存在的应用服务端口接入，而不是现在预测性拆分。

### 4.2 仓库组织建议

以下是后续脚手架任务应实现的建议边界，不是本任务创建的目录：

```text
backend/
  pyproject.toml
  uv.lock
  src/studypilot/
    api/                 # HTTP 路由、请求/响应模型、错误转换
    application/         # 用例编排、事务边界
    modules/
      resources/         # 资料和原始来源
      taxonomy/          # 主题与标签
      learning/          # 状态、进度和学习记录
      notes/             # 个人笔记
      reviews/           # 复习计划与复习结果
      analytics/         # 只读统计查询
    infrastructure/      # SQLAlchemy、SQLite、文件存储、配置、日志
    extension_ports/     # 后续解析、AI、RAG、Agent 接口占位；不含实现
  migrations/
  tests/
frontend/
  package.json
  package-lock.json
  src/
    app/                 # 路由、总布局、全局错误边界
```

`var/` 只是默认本地位置。真正路径应由配置给出，并在启动时解析为绝对路径。前端永远看不到服务器真实磁盘路径。

## 5. 核心技术选择及边界

### 5.1 FastAPI 与 REST API

选择原因：

- OpenAPI 自动文档让初学者可以在浏览器查看每个接口的输入、输出和错误。
- Python 类型提示可同时用于校验、编辑器提示和接口说明。
- 官方提供基于 TestClient 与 pytest 的测试方式；见 [FastAPI 测试文档](https://fastapi.tiangolo.com/tutorial/testing/)。
- 官方支持 `multipart/form-data` 文件上传；见 [FastAPI 文件上传文档](https://fastapi.tiangolo.com/tutorial/request-files/)。

不选择 GraphQL：第一阶段对象和操作边界明确，REST 更容易理解、调试和缓存；GraphQL 会增加查询语言、权限和客户端缓存复杂度。

版本策略：所有业务接口放在 `/api/v1`。`v1` 表示第一版公共 HTTP 契约，不等同于产品阶段。破坏兼容性的变更必须先改契约并建立迁移任务。

### 5.2 React、TypeScript 与 Vite

选择原因：

- React 组件适合复用资料卡、筛选条件、进度编辑、统计卡片和确认对话框。
- TypeScript 在运行前检查字段名称和类型，降低前端误用 API 数据的概率。
- Vite 提供开发服务器和正式构建；[Vite 官方入门文档](https://vite.dev/guide/)列出了 React/TypeScript 模板和开发、构建命令。
- React Router 只负责页面地址与界面切换；不引入全栈 React 框架，避免与 Python 后端职责重叠。

不选择 Next.js：当前不需要服务器端渲染、公开内容搜索优化或第二套服务器运行时。它会与 FastAPI 形成双后端心智负担。

不引入全局状态库：第一阶段以服务端数据为主，使用功能内状态、URL 查询参数和小型共享上下文即可。只有实际出现跨页面复杂客户端状态后才重新评估。

### 5.3 SQLite、SQLAlchemy 与 Alembic

选择原因：

- SQLite 是进程内、无独立服务器、零配置且支持事务的数据库；见 [SQLite 官方介绍](https://www.sqlite.org/about.html)。这与单用户本地 MVP 匹配。
- SQLAlchemy 让数据访问与具体数据库连接分离，并提供明确事务边界。[SQLAlchemy 会话文档](https://docs.sqlalchemy.org/en/20/orm/session_basics.html)强调一个 Session 表示可变、有状态的单个数据库事务，不能在并发任务间共享。
- Alembic 是 SQLAlchemy 的数据库迁移工具；见 [Alembic 官方文档](https://alembic.sqlalchemy.org/en/latest/)。迁移文件必须提交到 Git，开发者不能只修改自己的本地数据库。

事务是“一组数据操作要么全部成功，要么全部失败”。例如更新进度和追加学习记录必须在同一个事务内完成，不能出现进度已变但记录丢失。

不选择 PostgreSQL：它适合多人并发和在线服务，但第一阶段会增加数据库进程、账户、端口和备份运维。通过 SQLAlchemy 与迁移约束保留以后迁移可能，不为未来假设提前承担成本。

SQLite 限制：不允许在多个并行写入任务中共享同一个运行数据库文件；测试各自使用临时数据库。若以后出现真实高并发写入，再按测量证据迁移。

### 5.4 原始文件存储

数据库不保存大文件二进制本体，只保存：内部文件 ID、原始文件名、受控相对键、大小、媒体类型、SHA-256 校验值、创建时间和所属资料 ID。

实际文件保存为类似 `var/uploads/<resource-id>/<file-id>` 的服务器生成路径。原始文件名只用于显示和下载，不直接作为磁盘路径，防止文件名中的 `../` 等内容越过数据目录。

上传流程边界：

1. 接口层先检查请求类型和基础大小限制。
2. 文件存储服务以随机内部 ID 写入临时位置，并计算校验值。
3. 资料应用服务在数据库事务中建立资料与文件元数据。
4. 数据库失败时移除临时文件；文件落盘失败时不创建资料记录。
5. 正文解析不在此流程中，原件保存成功就可以完成基础资料添加。

下载只能通过受控 API 按文件 ID 获取。API 根据数据库记录解析文件，不能接受任意本机路径。

### 5.5 依赖管理与本地运行

后端使用 uv。其 [项目管理官方文档](https://docs.astral.sh/uv/guides/projects/)说明 `uv.lock` 记录精确依赖并应提交版本控制，`uv run` 会检查项目、锁文件与环境的一致性。

前端使用随 Node.js 提供的 npm，并提交 `package-lock.json`；自动检查和干净安装使用 `npm ci`。[npm 官方文档](https://docs.npmjs.com/cli/commands/npm-ci/)说明它要求锁文件与 `package.json` 一致且不会改写两者。

后续脚手架任务需要提供一个面向初学者的启动说明，并将实际版本写入仓库配置。建议开发模式：

```text
终端 1：在 backend 中启动 FastAPI，仅监听 127.0.0.1
终端 2：在 frontend 中启动 Vite，仅允许明确的本地 API 地址
浏览器：打开 Vite 给出的本地地址
```

正式演示构建时，前端产生静态文件，由 FastAPI 从同一站点提供。这样不需要额外云平台，也能避免演示环境的跨来源配置。

## 6. 第一阶段模块职责与所有权

| 模块 | 拥有的数据与规则 | 可以依赖 | 明确不负责 |
| --- | --- | --- | --- |
| 资料 `resources` | 学习资料元数据、来源类型、网页链接、粘贴原文、原始文件元数据、资料删除用例 | 分类查询、文件存储接口、学习清理接口 | 正文解析、AI 摘要、状态/进度规则、学习统计算法 |
| 分类 `taxonomy` | 主题、标签、资料—标签关系、主题/标签删除约束 | 数据仓储 | 资料状态和学习进度 |
| 学习 `learning` | `LearningProgress`、学习状态、当前进度、开始/完成时间、学习记录、进度变化不变量 | 只按资料 ID 验证资料存在 | 原始文件、笔记正文、复习日期 |
| 笔记 `notes` | 个人笔记内容、创建/更新时间、所属资料 | 只按资料 ID 验证资料存在 | AI 生成内容；两者必须保持不同类型和存储边界 |
| 复习 `reviews` | 当前复习计划、到期/逾期判断、复习结果历史、重新安排 | 资料存在性、学习状态变更用例 | 强制间隔重复算法 |
| 统计 `analytics` | 概览和主题统计的只读查询模型 | 读取资料、学习、复习聚合数据 | 修改任何源数据、保存重复统计真相 |
| API `api` | HTTP 路由、输入输出模式、状态码、统一错误格式 | 调用应用服务 | 直接执行 SQL、拼磁盘路径、实现业务判断 |
| 界面 `frontend` | 页面、交互状态、可访问性、确认对话框、API 调用 | 仅依赖 `/api/v1` 契约 | 直接访问数据库或把浏览器判断当作最终业务校验 |
| 基础设施 `infrastructure` | 数据库会话、仓储实现、迁移、配置、日志、文件存储适配 | 实现上层定义的接口 | 定义产品规则 |

### 6.1 依赖与所有权原则

- 一个事实只有一个权威所有者。例如当前进度由学习模块的 `LearningProgress` 修改，资料列表和统计模块只读取组合后的查询结果。
- 跨模块只传 ID、命令和明确的数据结构，不共享可随意修改的 ORM 对象。
- 删除资料由资料应用服务编排，各从属模块提供清理能力；界面不能分别调用多个删除接口来模拟事务。
- 统计默认实时聚合，不建立需要同步更新的“统计结果表”。真实性能不足后再依据测量引入缓存。
- 所有时间由后端保存为 UTC，界面按用户本地时区显示，避免以后跨时区时含义不一致。

## 7. 最小公共契约基线

本节定义足以拆分后续任务的行为边界，但不替代后续接口契约任务中的完整字段、示例和 OpenAPI 快照。

### 7.1 API 资源组

| API 资源组 | 最小职责 |
| --- | --- |
| `/api/v1/resources` | 新增链接、文件或粘贴内容；列表、详情、修改、搜索、筛选、排序、删除确认 |
| `/api/v1/topics` | 主题增删改查和删除冲突提示 |
| `/api/v1/tags` | 标签增删改查以及资料标签关联 |
| `/api/v1/resources/{id}/notes` | 某资料的个人笔记增删改查 |
| `/api/v1/resources/{id}/study-records` | 追加和查看学习记录；事务性更新状态与进度 |
| `/api/v1/reviews` | 到期/逾期列表、完成复习、重新安排、移出复习列表 |
| `/api/v1/analytics/overview` | 资料状态数量、当前学习、今日复习、最近资料与记录、本周时长 |
| `/api/v1/analytics/topics` | 每个主题的资料数量、完成比例和投入时间 |
| `/api/v1/files/{file-id}/download` | 校验归属后下载原始文件，不暴露磁盘路径 |

列表 API 统一支持分页，并只允许契约列出的筛选和排序字段。分页是把大量结果分批返回，避免资料变多后一次加载全部内容。

### 7.2 数据流与事务边界

#### 添加资料

```text
界面提交链接、文件或文本
→ API 校验互斥来源字段
→ 资料应用服务保存原件/原文和数据库记录
→ 分类模块建立主题、标签关联
→ 成功后返回完整资料摘要
```

一次资料必须且只能有一种主要来源：网页链接、上传文件或粘贴内容。部分失败不能留下用户看不到的半成品记录。

#### 记录学习

```text
界面提交学习时间、时长、前后进度、状态和备注
→ 学习模块验证 0%～100%、时间非负、状态转换合法
→ 同一数据库事务内追加学习记录并更新 LearningProgress 当前值
→ 返回新状态和本次记录
```

#### 完成复习

```text
界面提交复习结果和可选的下次日期
→ 复习模块追加不可覆盖的结果记录
→ 更新或关闭当前复习计划
→ 需要时通过学习模块更新“待复习”状态
```

### 7.3 错误契约

所有 API 错误转换为稳定外形：

```json
{
  "error": {
    "code": "RESOURCE_NOT_FOUND",
    "message": "没有找到这份资料。",
    "details": {},
    "request_id": "用于排查问题的随机编号"
  }
}
```

- `code` 供前端稳定判断；不能让前端依赖可能变化的中文句子。
- `message` 面向用户，不包含堆栈、磁盘路径、SQL、笔记正文或密钥。
- `details` 只提供安全的字段级校验信息。
- 未找到使用 404，状态冲突使用 409，普通输入错误使用 422，超限文件使用 413，未知错误使用 500。
- 500 错误在服务端以 `request_id` 关联详细诊断，但日志仍需脱敏。

前端必须提供页面级错误边界和可重试提示。错误边界是“某个界面出错时显示受控提示，而不是让整个应用白屏”的保护层。

### 7.4 删除与用户确认边界

删除资料至少分为两步：

1. 前端获取删除影响摘要，显示将删除的资料、原始文件、笔记、学习记录和复习记录数量。
2. 用户主动确认后，前端发送包含该资料 ID 的确认值；后端验证确认值与目标一致后，才执行统一删除用例。

后端不能因为前端已经弹窗就省略确认校验。删除过程中若磁盘或数据库操作失败，应保留或恢复原件并返回明确失败，不能谎称删除成功。具体的暂存、回滚与重试算法由后续文件契约任务细化并测试。

主题或标签仍被资料使用时，默认返回 409 和影响数量，不静默连带删除资料。

### 7.5 原始文件处理边界

- 第一阶段只负责保存、下载和删除原件，不声称已读取正文。
- 文件扩展名、浏览器上传的媒体类型和原始文件名都是不可信输入。
- 文件大小上限、允许类型识别和恶意内容扫描策略由后续文件契约任务明确；在契约确定前不能开放任意上传。
- 后续解析模块只能读取文件存储服务提供的只读流，并把处理状态和派生文本写入自己的边界。
- 解析失败只改变解析状态，不得修改或删除 `OriginalFile`。

### 7.6 后续 AI、RAG 与 Agent 的扩展端口

第一阶段只保留接口位置，不创建实现、队列表或假的 AI 数据：

- `ContentReaderPort`：按资料 ID 获取用户明确允许处理的只读内容。
- `GeneratedContentWriterPort`：保存明确标记为 AI 生成且关联原资料的派生内容，不能写入个人笔记。
- `RetrievalPort`：在用户指定资料范围内返回片段与来源定位。
- `StudyActionProposalPort`：只产生拟执行动作；任何新增、修改、完成或删除用户数据都必须再次确认。
- `SecretProviderPort`：提供密钥的存取与遮罩，业务模块只拿短时使用值，不知道实际保存位置。

“Port（端口）”在这里不是网络端口，而是一份能力接口：调用者只知道能做什么，不依赖具体由本地代码、后台任务还是外部服务完成。

## 8. 核心数据对象概念模型

这是概念级模型，用于统一含义，不是最终数据库迁移文件。

```text
Topic 1 ──────── 0..* LearningResource  （每份资料可选择 0..1 个 Topic）
Tag   0..* ───── 0..* LearningResource  （通过 ResourceTag）

LearningResource 1 ─── 0..1 OriginalFile
LearningResource 1 ─── 1 LearningProgress
LearningResource 1 ─── 0..* Note
LearningResource 1 ─── 0..* StudyRecord
LearningResource 1 ─── 0..* ReviewRecord
LearningResource 1 ─── 0..1 ActiveReviewPlan
```

### 8.1 对象与关键含义

| 对象 | 第一阶段关键字段 | 关系与不变量 | 后续需细化 |
| --- | --- | --- | --- |
| `LearningResource` 学习资料 | ID、标题、来源类型、原始链接或粘贴原文、来源名称、保存原因、主题 ID、创建/更新时间 | 恰好一种主要来源；主题可为空后补；只拥有资料元数据，不直接拥有学习规则 | 各类型长度上限、搜索索引、乐观并发字段 |
| `OriginalFile` 原始文件 | 文件 ID、资料 ID、原始名称、内部存储键、大小、媒体类型、SHA-256、创建时间 | 一份文件型资料对应一个原件；内部存储键唯一；不保存客户端绝对路径 | 上传上限、内容识别、备份与恢复细节 |
| `LearningProgress` 学习进度 | 资料 ID、当前状态、当前进度、开始时间、完成时间、更新时间 | 每份资料恰有一条；进度 0～100；由 learning 模块维护并与 `StudyRecord` 事务性更新 | 状态转换表、并发更新策略、各时间自动填充规则 |
| `Topic` 主题 | ID、名称、说明、创建/更新时间 | 一个资料至多一个主要主题；名称在规范化后唯一 | 大小写和空白规范、删除/转移流程 |
| `Tag` 标签 | ID、名称、创建/更新时间 | 标签名称规范化后唯一；可关联多份资料 | 颜色是否属于产品需求尚未确认，不加入当前模型 |
| `ResourceTag` 资料标签关联 | 资料 ID、标签 ID | 复合唯一，避免同一标签重复添加 | 无额外业务字段时保持纯关联 |
| `Note` 个人笔记 | ID、资料 ID、正文、创建/更新时间 | 只能由用户笔记操作修改；与 AI 生成内容分表或分边界 | Markdown 支持、版本历史、最大长度 |
| `StudyRecord` 学习记录 | ID、资料 ID、学习开始时间、时长、进度前值/后值、状态前值/后值、阶段总结、疑问/下一步、创建时间 | 重要状态/进度变化必须追加；历史记录不因资料当前值变化而重写 | 同日合并规则、编辑历史、最小时间单位 |
| `ActiveReviewPlan` 当前复习计划 | 资料 ID、下次复习时间、状态、创建/更新时间 | 每份资料最多一个当前计划；日期由用户决定 | 提醒时区、未来算法字段 |
| `ReviewRecord` 复习结果 | ID、资料 ID、计划日期、实际完成时间、结果备注、完成后安排 | 追加历史，不用新计划覆盖旧结果 | 结果枚举、复习时长是否复用学习记录 |
| `GeneratedContent` AI 生成内容 | 第一阶段不存在数据表 | 未来必须关联资料并明确 `generated` 来源，绝不能覆盖 Note | 第二阶段单独契约 |
| `LearningTask` 学习任务 | 第一阶段不存在数据表 | 直到第三阶段用户确认需求后再设计 | 第三阶段单独契约 |

### 8.2 状态与派生值

资料状态沿用需求中的五个值：`未读`、`学习中`、`已完成`、`待复习`、`已归档`。数据库保存稳定英文代码，API 同时提供中文显示标签，避免以后仅改文案就破坏数据。

- `未读` 默认进度为 0，但后续契约需决定用户是否可保留非零进度后手动改回未读。
- 进度达到 100% 不应在没有确认的情况下自动标记完成；可以提示用户选择。
- “今天到期”“逾期”“本周学习时长”“主题完成比例”属于按时间或记录计算的派生值，不重复保存为权威字段。
- 资料 `updated_at` 不应因为单纯查看或下载而改变。

上述仍需细化之处必须由后续契约任务决定，当前不能由实现 Agent 各自猜测。

## 9. 安全、隐私与重要数据边界

### 9.1 Git 与配置

- `var/`、数据库文件、上传文件、导出文件、`.env`、测试临时数据和日志必须加入 `.gitignore`。
- 仓库只提交 `.env.example` 一类不含真实值的说明文件。
- 日志配置、错误报告和测试夹具不得使用真实个人资料或密钥。
- 依赖锁文件应提交；它们是版本信息，不是秘密。

### 9.2 本地访问边界

- 第一阶段只监听 `127.0.0.1`，即只有本机可连接；不得默认绑定 `0.0.0.0` 暴露给局域网。
- 开发期 CORS 只允许明确的本地前端地址，不使用 `*`。
- 第一阶段没有账户登录，**因此不能直接部署到公网**。任何联网部署必须先建立身份认证、授权、HTTPS、上传限制和备份任务。

### 9.3 原始文件和笔记

- 原始文件、粘贴原文和个人笔记均视为私人数据。
- 正常日志只记录资源 ID、操作结果、耗时和错误编号；默认不记录标题、正文、笔记和完整文件名。
- 下载响应设置安全的文件名与内容类型，不能执行用户上传内容。
- 文件存储接口必须验证最终路径仍在受控根目录内，防止路径穿越。
- 第一阶段至少提供清晰的数据目录说明和人工备份/恢复方法；自动备份是否加入产品需求需另行确认。

### 9.4 未来 API Key

第一阶段不收集 API Key。第二阶段实现时：

- 默认使用操作系统凭据存储保存密钥；数据库只保存服务商、密钥引用和脱敏提示。
- 开发环境可以从未提交的环境变量读取密钥，但不能把 `.env` 作为面向用户的正式密钥库。
- API 返回值、界面、日志和异常只显示遮罩值，不能返回完整密钥。
- 模型调用前向用户说明将使用哪个服务和哪些资料；删除密钥后引用必须失效。

若目标平台的系统凭据存储不可用，必须先由独立安全任务评估加密存储方案，不能退化为明文数据库。

## 10. 测试与质量策略

### 10.1 测试分层

| 层级 | 工具 | 必须证明的内容 |
| --- | --- | --- |
| 领域/应用服务单元测试 | pytest | 状态与进度约束、到期判断、统计计算、确认规则，不依赖真实磁盘或网络 |
| 仓储和文件集成测试 | pytest + 临时 SQLite/临时目录 | 事务回滚、关系约束、迁移、文件保存/清理、路径安全 |
| API 契约测试 | FastAPI TestClient | 状态码、请求响应结构、分页筛选、错误外形、上传和下载 |
| 前端组件测试 | Vitest + React Testing Library | 用户能看到正确状态、提交表单、处理失败、完成删除确认 |
| 端到端测试 | Playwright | 浏览器中完成“添加→分类→学习→笔记/记录→完成→复习→统计”主闭环 |

[Vitest 官方指南](https://vitest.dev/guide/)说明它复用 Vite 配置并支持 TypeScript；[React Testing Library 官方说明](https://testing-library.com/docs/react-testing-library/intro/)强调通过用户可见的 DOM 操作测试组件；[Playwright 官方文档](https://playwright.dev/docs/intro)将其定义为现代 Web 应用的端到端测试框架。

### 10.2 必测风险场景

- 三种来源类型的资料添加，及“同时提交两种来源”的拒绝。
- 文件落盘失败和数据库失败都不产生半成品。
- 进度小于 0、大于 100、负学习时长、非法状态值被拒绝。
- 更新状态/进度时学习记录与当前值要么一起成功，要么一起失败。
- 未确认删除、确认目标不匹配、关联主题仍被使用时被拒绝。
- 今日到期与逾期边界、跨日和时区显示。
- 搜索、组合筛选、排序、分页结果稳定。
- 统计值能从底层记录重新计算，不依赖手工维护的缓存。
- 错误响应和日志不泄露磁盘路径、正文、笔记或未来密钥。
- 原始文件可下载且校验值一致，解析能力不存在时不显示“已解析”。

### 10.3 第一阶段完成门槛

- 后端格式化、静态检查、类型检查和 pytest 命令全部通过；准确命令由脚手架任务建立后写入模块规则。
- 前端格式化、lint、TypeScript 检查、Vitest 和正式构建通过。
- 至少一个 Playwright 主闭环通过。
- OpenAPI 契约变更得到审查；数据库从空库执行全部迁移成功。
- 没有把尚未建立的命令写成已通过事实。本提案只定义后续必须建立的检查类型。

## 11. 需求—架构逐项追踪

### 11.1 第一阶段功能追踪

| 需求位置 | 已确认行为 | 架构承载 |
| --- | --- | --- |
| 5.1 添加资料 | 网页、PDF、Word、Markdown、TXT、粘贴内容；保留原件 | `resources`、`OriginalFile`、multipart 上传、受控文件目录；解析明确延期 |
| 5.2 基本信息 | 标题、来源、主题、标签、原因、状态、进度和时间 | `LearningResource`、`LearningProgress`、`Topic`、`Tag` 与后端校验 |
| 5.3 资料库 | 列表/卡片、详情、修改、删除、打开链接、下载文件 | 资源 API、文件下载 API、React 视图、两步删除确认 |
| 5.4 分类搜索筛选 | 主题/标签管理、组合筛选、排序、正文以后加入 | taxonomy 模块、分页列表契约；第一阶段只检索已保存元数据，正文索引留给解析阶段 |
| 5.5 状态进度 | 五状态、0～100%、保留变化 | learning 模块、当前值 + 追加 `StudyRecord`、单事务 |
| 5.6 个人笔记 | 多条笔记增删改查，区别 AI 内容 | notes 独立所有权；AI 内容不进入 Note |
| 5.7 学习记录 | 时间、时长、前后进度、总结、疑问，按资料和时间查看 | `StudyRecord` 与资源/近期记录 API |
| 5.8 复习管理 | 到期、逾期、完成结果、重新安排、移出 | `ActiveReviewPlan` + `ReviewRecord`，用户决定日期 |
| 5.9 概览统计 | 状态数量、当前学习、今日复习、最近记录、本周时长、主题统计 | analytics 只读聚合，不保存第二套事实 |
| 5.10 页面入口 | 概览、资料库、添加、详情、学习记录、主题统计 | React Router 页面边界和功能组件 |

“按标题或关键词搜索”在第一阶段的关键词范围建议限定为标题、来源名称和保存原因；笔记是否进入统一搜索需要后续契约明确。正文只有解析成功后才进入搜索，不能把尚未实现的正文检索写成第一阶段能力。

### 11.2 核心原则追踪

| 项目原则 | 架构保证 |
| --- | --- |
| 个人使用优先 | 本地单用户、SQLite、本地文件，不建设账户和团队系统 |
| 先管理后智能 | extension ports 只有接口边界，没有解析、AI、RAG 或 Agent 实现 |
| 学习过程优先 | 学习记录、复习历史和统计是一级模块，不把产品简化成收藏夹 |
| AI 输出可验证 | 未来生成内容与原资料关联，RAG 端口必须返回来源；第一阶段不伪造能力 |
| 用户保留控制权 | 删除后端二次校验；未来 Agent 只提案，修改数据前确认 |
| 展示不等于运营 | 提供本地演示构建和 API 文档，不选云平台或公网运营能力 |
| 保留未来空间 | 模块和端口隔离具体实现，但不预建微服务、队列或向量库 |

本提案没有新增公开多用户、支付、商业化、移动端、自动抓取、云部署或未经确认自动修改数据等范围。

## 12. 从架构基线到可运行 MVP 的任务顺序

任何后续任务都需单独任务单、唯一写入 Agent、独立只读审查和验收。最多同时运行两个写入型 worktree 任务。

### 阶段 A：先冻结共享基础，不能并行跳过

1. **建议任务 A：仓库与本地运行脚手架**
   - 建立 backend/frontend 最小结构、版本文件、锁文件、Git 忽略、统一启动与检查说明。
   - 只做到健康检查和空页面，不实现业务。
2. **建议任务 B：API 与数据契约基线**
   - 细化字段、枚举、状态转换、错误代码、分页筛选、时间语义、删除协议和 OpenAPI 示例。
   - 建立概念模型对应的初始 SQLAlchemy 模型与 Alembic 迁移可以作为同一任务或紧随其后的独立数据库任务；在其冻结前业务模块不能各自建表。
3. **建议任务 C：共享测试基础**
   - 建立临时数据库、临时文件目录、API 客户端、前端测试和最小端到端测试骨架。

API 与数据契约基线必须先于跨模块功能实现，因为后续 Agent 都会依赖同一字段和错误含义。具体任务编号仍由 `coordinator` 分配，本提案不预占编号。

### 阶段 B：在契约稳定后可有限并行

可并行组 1（路径和契约互不重叠时）：

- **资料/分类后端**：资料、主题、标签、搜索筛选、原始链接和粘贴内容。
- **前端应用壳**：路由、布局、通用 API 客户端、错误边界和空页面入口。

可并行组 2（资料 ID 契约和初始迁移已稳定后）：

- **原始文件后端**：上传、保存、下载、校验和删除回滚。
- **学习与笔记后端**：状态、进度、学习记录、个人笔记。

同一 Alembic 迁移目录不能由多个 Agent 并行写入。新增表结构应由数据契约/迁移所有者串行提交，功能 Agent 只实现已存在模型或等待迁移合并。

### 阶段 C：依赖基础记录，必须后置

1. 复习后端与界面：依赖资料和学习状态。
2. 统计后端：依赖资料、学习记录和复习数据均稳定。
3. 各功能前端：按已冻结 API 契约实现资料库、详情、记录、复习和统计页面。
4. 主闭环集成：补全跨页面 Playwright 测试、错误恢复和初学者运行说明。
5. MVP 阶段验收：从空数据目录启动，真实走完整闭环，检查隐私、原件、删除和统计证据。

### 阶段 D：第一阶段合并后再考虑

正文解析、API Key、AI 阅读、练习题、RAG 和学习 Agent 必须分别立项。它们不能与第一阶段“为了预留接口”一起偷偷实现。

## 13. 主要风险与用户需要关注的取舍

| 风险或取舍 | 当前控制方式 | 触发后续行动的事实 |
| --- | --- | --- |
| 前端学习曲线比 Django 模板高 | 限制为 React/TypeScript/Vite/Router，不加大型状态库和 UI 框架；分阶段学习 | 用户在脚手架/首个页面后明确认为成本妨碍可用性 |
| 前后端契约漂移 | OpenAPI 为外部契约，契约任务先行，API 测试和前端类型检查共同把关 | 出现字段含义不一致或多个 Agent 重复定义类型 |
| SQLite 并发写限制 | 单用户本地使用，每请求独立 Session，测试数据库隔离 | 出现多用户、多进程高频写入或锁等待测量证据 |
| 文件系统与数据库无法天然成为同一事务 | 临时文件、数据库事务、失败清理和可重试删除协议 | 故障注入测试发现原件丢失或孤儿文件无法恢复 |
| 本地无登录不等于安全上线 | 只绑定本机，明确禁止直接公网部署 | 用户决定远程访问或公开演示 |
| 两套语言生态增加依赖维护 | uv 与 npm 各自锁定，更新作为独立任务并执行完整测试 | 安全公告、运行时结束支持或依赖冲突 |
| 未来 AI 任务可能阻塞 Web 请求 | 当前不实现；只保留端口 | 真实解析/模型调用超过可接受等待并需要重试 |
| 统计查询随数据增长变慢 | MVP 实时聚合，先正确后优化 | 性能测试证明查询超出已确定体验目标 |

用户在合并本提案前需要特别确认的核心取舍是：**接受比 Django 方案更高的前端学习成本，换取独立 API 学习、清晰跨模块契约和未来 AI/RAG 复用边界。**

## 14. 术语速查

| 术语 | 面向初学者的解释 |
| --- | --- |
| MVP | 最小可用产品；不是功能残缺的演示，而是先完成一条可以实际使用的核心流程 |
| 前端/后端 | 前端是用户在浏览器看到和操作的界面；后端负责校验规则、保存数据和提供 API |
| API | 不同程序之间约定好的调用入口；这里是浏览器界面向 Python 后端读写资料的方式 |
| HTTP | 浏览器与后端通信所用的通用协议，规定请求方法、地址、状态码和响应内容 |
| URL | 一个网页或 API 入口的地址 |
| REST | 用网址、HTTP 方法和状态码表达“读取、创建、修改、删除”资源的一种常见 API 风格 |
| CRUD | Create、Read、Update、Delete 的缩写，即新增、查看、修改和删除四类基础操作 |
| JSON | 前后端交换结构化数据的文本格式，类似带固定字段的电子表单 |
| OpenAPI | 描述 API 有哪些入口、字段和错误的标准文件，可生成交互式说明页面 |
| SPA | 单页应用；页面切换主要由浏览器中的 JavaScript 完成，不代表只有一个功能页面 |
| ORM | 对象关系映射；让 Python 类与数据库表对应，减少散落的 SQL，同时不取消数据库规则 |
| SQL | 关系数据库用来查询和修改数据的语言 |
| 数据库迁移 | 可按顺序执行的数据库结构变更记录，例如新增一列或一张表 |
| 事务 | 一组操作全部成功才生效，任何一步失败就整体撤销 |
| CORS | 浏览器控制“一个地址的前端能否访问另一个地址后端”的安全规则 |
| 契约 | 模块共同遵守的输入、输出、错误和数据含义；它比函数名称更重要 |
| 端口/适配器 | 上层先定义需要的能力，底层再用 SQLite、本地文件或未来外部服务实现 |
| 端到端测试 | 像真人一样在浏览器执行完整流程，检查多个模块合起来是否可用 |
| 锁文件 | 记录实际安装的精确依赖版本，使不同机器得到一致环境 |
| UTC | 全球统一的时间基准；后端按它保存时间，界面再换算成本地时间 |
| SHA-256 | 根据文件内容计算的固定长度校验值；内容变化时值会改变，可用来检查原件是否一致，但它不是加密文件 |
| 静态检查/lint | 不运行完整程序就查找代码错误和不符合规则之处的自动检查 |
| CORS 来源 | 协议、域名和端口的组合；即使都叫 localhost，端口不同也是不同来源 |
| 派生值 | 可以从权威原始记录计算出的结果，例如本周学习时长，不应人工维护第二份真相 |

## 16. 提案决策摘要

1. 第一阶段采用本地单用户模块化单体，不采用微服务、云平台或多用户架构。
2. 后端使用 FastAPI + SQLAlchemy + Alembic，数据库使用 SQLite，原始文件使用本地受控目录。
3. 前端使用 React + TypeScript + Vite + React Router，通过 `/api/v1` REST API 与后端交互。
4. uv 与 npm 分别锁定后端和前端依赖；pytest、Vitest 和 Playwright 覆盖分层测试。
5. 资料、分类、学习、笔记、复习、统计和界面拥有独立职责，跨模块通过应用服务和契约协作。
6. 删除必须同时具备可见确认和后端确认校验；文件、笔记和未来密钥不得进入 Git 或普通日志。
7. 后续解析、AI、RAG 和 Agent 只保留端口，不在第一阶段实现。
8. 下一个开发阶段先建立脚手架，再冻结数据/API 契约，之后才有限并行开发功能。
