## 2. 背景与依据

StudyPilot 已完成项目背景、产品需求和多 Agent 开发制度的确认，但尚未确定应用技术栈、模块组织和跨模块契约。根据 [项目需求说明](../../项目需求说明.md) 第 2、3、5、8 节，第一阶段必须先实现资料管理与学习过程管理的完整闭环；根据 [项目背景与介绍](../../项目背景与介绍.md) 第 2、5、6 节，方案还需兼顾个人实际使用、Python/AI 学习路线、作品展示价值和未来扩展空间。

本任务由 `architecture_owner` 在已确认需求范围内提出可执行的 MVP 架构方案，为后续仓库脚手架、资料模块、学习模块和前端任务提供统一依据。

## 3. 目标

- 形成一份可由用户理解和决定是否采纳的第一阶段 MVP 架构与技术选型提案；
- 比较可行方案并给出有证据的推荐，而不是只列技术名称；
- 明确前端、后端、数据、原始文件、测试和本地运行的技术边界；
- 明确资料管理、学习过程管理和界面层之间的模块职责与最小契约；
- 给出支持后续内容解析、AI、RAG 和学习 Agent 的扩展边界，但不提前实现这些功能；
- 把架构拆成可以继续建立独立开发任务的实施顺序。

## 4. 非目标

- 不创建应用代码、目录脚手架、数据库迁移、接口实现或页面；
- 不安装依赖，不修改开发环境、CI、GitHub 设置或部署配置；
- 不修改已确认的项目背景和产品需求；
- 不新增公开多用户、团队协作、支付或商业化需求；
- 不实现内容解析、AI、RAG 或学习助手 Agent；
- 不选择正式生产云平台，也不承诺上线、工期或成本；
- 不把未经用户最终合并确认的提案描述成已经生效的架构决定。

## 8. 功能要求

1. 从已确认需求提取架构约束，包括个人使用优先、Python 学习目标、第一阶段完整闭环、原始文件保留、删除确认、隐私保护和后续 AI 扩展。
2. 至少比较两套真实可行的技术方案，并从学习成本、开发复杂度、需求适配、测试难度、本地运行、作品展示和未来扩展角度说明取舍。
3. 给出单一推荐方案，明确后端、前端、数据库、原始文件存储、API 形式、依赖管理、测试方式和本地运行方式；不得同时保留多个“最终方案”。
4. 说明选择每项核心技术的原因、未选择主要替代方案的原因，以及未来什么条件下才需要重新评估。
5. 定义第一阶段模块边界，至少覆盖资料、主题与标签、学习状态与进度、笔记、学习记录、复习、统计和界面层；不得把所有逻辑归入一个无边界模块。
6. 定义足够指导后续任务拆分的最小契约，包括模块间数据流、所有权、错误边界、原始文件处理边界和用户确认边界；不要求写实现级接口代码。
7. 给出核心数据对象及关系的概念模型，覆盖需求文档第 4 节中与第一阶段相关的对象，并说明哪些字段或关系仍需在后续契约任务中细化。
8. 说明 API Key、原始文件、用户笔记等敏感或重要数据的安全边界，禁止把秘密写入仓库或日志。
9. 给出从架构基线到可运行 MVP 的建议任务顺序，明确哪些任务可并行、哪些任务必须等待公共契约确定。
10. 面向开发经验不足的用户解释关键术语；每个重大选择必须说明它解决的实际问题。
