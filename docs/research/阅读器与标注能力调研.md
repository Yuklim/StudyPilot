## 2. 参照产品的核心论证

Readwise Reader 在公开 Beta 说明中给出的立论不是「阅读体验更好」，而是**解绑（unbundling）**：

> "even if we achieved a 10x improvement in a single silo, such as ebooks, that might only comprise 10% or 20% of your digital reading."

即：把单一格式做到十倍好，也只覆盖用户阅读总量的 10%–20%，收益不在深度而在**消除格式间的切换**。

这一论证补足了《项目背景与介绍》4.1 节的缺口。该节已识别「资料分散且容易失去上下文」，但解法停留在「统一保存」。参照产品的主张更进一步：

> 只要用户仍需跳出应用去阅读，上下文的断裂就没有真正解决——阅读过程中的理解不会落回资料本身。

对 StudyPilot 的意义：4.3 节「阅读过程缺少沉淀与复习」与 4.1 节其实是同一个问题的两面。心得之所以难沉淀，部分原因正是阅读发生在应用之外。

### 2.1 内容分区：Library 与 Feed

参照产品将内容分为两区，交互模式不同：

| 分区 | 内容 | 交互模式 |
| --- | --- | --- |
| Library | 手动收藏的高信号内容（文章、PDF） | 精读、标注、长期保留 |
| Feed | 自动到达的低信号内容（newsletter、RSS） | 快速筛选、大量丢弃 |

**StudyPilot 当前只有 Library 一侧，且建议维持现状。** 项目定位第 5 节已明确排除「只保存链接的浏览器收藏夹」与信息流形态。此处记录该二分的价值在于一条设计约束：

> 高信号与低信号内容若混在同一列表中，高信号内容会被稀释。若未来引入任何自动来源（如 RSS、订阅），必须与手动收藏物理分区，而非仅用标签区分。

## 3. 关键架构约束：保存即冻结

参照产品的 Parsing 文档记载了一条明确的设计决定：

> Reader intentionally never re-parses saved content, **preserving original context for highlights and notes**. Users must delete and re-save articles to obtain updated versions.

即：**已保存内容永不重新解析**。想更新只能删除后重存，连同该文档上的全部标注一并丢失。

### 3.1 冻结的准确含义

「冻结」约束的是**标注绑定在哪个版本的内容上**，不是「用户看不到最新内容」。二者常被混为一谈，此处明确区分。

标注锚定在正文内容上，正文一旦变化，锚点即失效或漂移。因此「保存」这一动作的语义必须是**存下一份当时的正文快照**，而不是「记录一个 URL，以后再取」。

两种保存语义的差异：

| 保存语义 | 内容永远最新 | 标注可长期存活 | 原文失效后仍可读 |
| --- | --- | --- | --- |
| 存 URL，读时抓取 | 是 | 否 | 否 |
| 存正文快照 | 否 | 是 | 是 |

真正不可兼得的只有一处：**原文更新后，标注无法自动迁移到新版本**。没有可靠方法把「针对旧版某一段写的批注」搬到改写后的新版上。

但「看最新内容」这件事并不需要牺牲：保留原始 URL 并提供「打开原文」入口即可。详见 7.1 节。

### 3.1.1 内容陈旧对学习工具反而是正确行为

用户的笔记是针对**保存时那个版本**写的。若强行显示最新版本，笔记会与正文对不上，看起来像是当时理解有误；显示快照则忠实保留了当时的学习状态。

对以「沉淀理解」为目标的产品，资料库应当是**用户的学习史**，而不是一份自动同步的最新文档镜像。这与《项目背景与介绍》原则 3「内容优先于过程数字」方向一致。

### 3.1.2 该取舍仅对网页类资料成立

上传的 PDF、Word、Markdown 文件存放在本地受控目录，本身不会变化，**天然处于冻结状态**，不存在此项取舍。

用户已确认的两个优先格式中：技术网页文章受此约束，PDF 不受。

### 3.2 对 StudyPilot 的直接影响

当前资料模型若仅保存 URL 与元数据，则未来引入标注时，**全部存量资料将不具备可锚定的内容基础**——标注功能对老数据直接不可用，且无法事后补救（原文可能已改版或失效）。

因此：**「保存资料时同时抓取并存储一份正文快照」这件事，越早做成本越低。** 它与阅读器功能可以完全解耦——先只存不显示，也已经保住了未来的可能性。

## 4. 抓取方式：浏览器扩展是解析质量的分水岭

参照产品文档明确指出：

> "If you save documents using the browser extensions on web or using the Safari browser and share sheet on iOS, these methods will generally result in the **highest quality parsing** because Reader is getting the full document content rather than the naked URL."

后端直接 fetch URL 与浏览器扩展的差距有三层，后两层是纯后端方案**无法弥补**的：

| 差异 | 后端 fetch | 浏览器扩展 |
| --- | --- | --- |
| 拿到的内容 | 初始 HTML | JS 渲染后的完整 DOM |
| 登录态 | 无 | 有（付费墙、需登录内容可正常保存） |
| 用户上下文 | 无 | 知道当前滚动位置、选区 |

### 4.1 对 StudyPilot 目标站点的判断

用户主要资料来源为知乎、CSDN、官方文档、GitHub。其中：

- **知乎、CSDN**：反爬严格 + 大量客户端渲染，纯后端抓取成功率预计明显偏低；
- **官方文档站**：多为 SPA（单页应用，内容由 JS 动态生成），后端 fetch 常常只能拿到空壳；
- **GitHub、静态博客**：后端 fetch 基本可用。

用户已确认**愿意做浏览器扩展**。据此建议：扩展不必与阅读器同期交付，但可以**先于阅读器**独立上线——它单独就能提升「收集」环节的质量，且正好承担第 3.2 节的正文快照抓取职责。

### 4.2 需要预先知道的成本

参照产品坦承 `"it's still not possible to parse the open web 100% correct 100% of the time"`，并**配置了一名工程师专职处理解析工单**。

解析是长尾问题，不存在「做完即完成」的状态。个人项目应据此降低预期：接受一定失败率，并提供**手动粘贴正文**作为兜底路径，而不是追求全站点覆盖。

## 5. 标注锚定：本方向的真正技术门槛

「能预览」实现难度不高，「标注能长期存活」才是门槛。

问题定义：用户高亮一段文字后，系统应存储什么？

- 存字符偏移 → 内容或渲染方式一变即错位；
- 存 DOM 路径 → 换一种渲染实现即全部失效。

### 5.1 分层选择器（W3C Web Annotation Data Model）

业界成熟解法是 W3C Web Annotation Data Model 的分层选择器，Hypothesis 等标注产品均采用。创建标注时**同时写入多种选择器**：

```json
{
  "selector": [
    {
      "type": "TextQuoteSelector",
      "exact":  "font-feature-settings: tnum",
      "prefix": "每个金额单元格都使用 ",
      "suffix": "，这是品牌在悄悄传递…"
    },
    {
      "type": "TextPositionSelector",
      "start": 4821,
      "end": 4850
    }
  ]
}
```

- `TextQuoteSelector`：主锚点。`exact` 为高亮原文，`prefix`/`suffix` 为前后文，用于同一文本多次出现时消歧。
- `TextPositionSelector`：降级锚点，字符偏移。内容上方有增删时会失效，但配合模糊匹配仍可定位。

重新定位时逐级降级：

1. `exact` 在全文中唯一匹配 → 命中；
2. 匹配多处 → 用 `prefix`/`suffix` 消歧；
3. 仍失败 → 用 `TextPositionSelector` 附近做模糊匹配；
4. 全部失败 → 标记为 **orphaned**（孤立标注）。

**第 4 步不可省略。** 孤立标注必须保留笔记内容并向用户显示「原文位置已找不到」，而不是静默丢弃。用户写下的理解比锚点更有价值。

### 5.2 渲染：使用 CSS Custom Highlight API

传统做法是向 DOM 插入 `<mark>` 或 `<span>` 包裹高亮文本，存在三个实际问题：

- **性能**：一段 200 行、每行约 8 个 token 的代码块会产生约 1600 个 wrapper 节点，每个都触发布局计算；
- **无障碍**：辅助技术需遍历被打碎的 DOM 树；
- **重叠**：两条高亮交叉时需要拆分节点，实现复杂且易错。

CSS Custom Highlight API 直接对 Range 对象着色，**不插入任何节点**：

```js
const highlight = new Highlight(range1, range2)
CSS.highlights.set('note', highlight)
```

```css
::highlight(note) { background: #f0e6c8; }
```

浏览器支持（截至 2026-09）：

| 浏览器 | 支持起始版本 |
| --- | --- |
| Chrome / Edge | 105（2022-08） |
| Safari | 17.2（2023-12） |
| Firefox | 149（2026-03） |

已达 Baseline 2025。已知限制：Firefox 上 `text-decoration` 与 `text-shadow` 对高亮不生效；`background-color`、`color`、`font-weight` 全部支持——满足本项目需求。

对本项目为新建功能、无历史包袱，建议**直接采用该 API，不走 DOM 包裹路线**。

## 6. 分格式渲染选型

用户已确认优先级为：**技术网页文章 + PDF（论文/电子书）**。

| 格式 | 建议方案 | 解决的实际问题 |
| --- | --- | --- |
| 网页 | **Defuddle** | Obsidian Web Clipper 团队维护。相比 Mozilla Readability 更宽容（多趟检测，误删更少），并将脚注、代码块、数学公式标准化为一致的 HTML 结构，可输出 Markdown。技术类文章场景明显更合适 |
| 网页（备选） | Mozilla Readability | 老牌稳定，驱动 Firefox 阅读视图。缺点是删除过于激进、无元数据提取、无 Markdown 输出 |
| PDF | PDF.js + 自绘高亮层 | 从 text layer 取选区 → 转换为 PDF 坐标 → 用 React portal 渲染覆盖层。可参考 react-pdf-highlighter |
| Markdown / 粘贴片段 | 直接渲染 | 无解析成本，适合最先打通整条链路 |
| Word | mammoth.js 转 HTML | 转换后复用网页链路 |
| EPUB | epub.js / foliate-js | 锚点使用 EPUB CFI，与 TextQuoteSelector 是另一套体系 |

### 6.1 PDF 与网页是两套锚定逻辑

需明确记录的差异：

- **网页/Markdown**：锚点是**文本**（TextQuoteSelector），与排版无关；
- **PDF**：锚点是**坐标**（页码 + 矩形区域），与页面布局绑定。

两者无法共用同一套锚定实现，数据模型需要能容纳两种 selector 形态。这是选型阶段就应确定的边界，不宜事后统一。

### 6.2 已知限制：扫描版 PDF

文字以图片形式存在的扫描件没有 text layer，**无法选中，也无法标注**。参照产品同样受限。若用户资料中扫描版教材占比高，需要引入 OCR，属独立的成本项，本文不展开。

## 7. 对当前代码的最小影响建议

用户在**本文写作当时（2026-09-05）**的决定为「还在评估，先不动代码」。本节仅记录当时的建议，不构成待办。**此后的实际进展见 1.4 节** —— 本节 7.1 的方向已经落地，读本节时不要把它当成尚未开始的事。

以下两项**不依赖阅读器功能，但事后无法为存量数据补做**：

### 7.1 正文快照 + 原文链接（用户已确认方向）

2026-09-05 用户确认采用「快照 + 原文链接」形态。这是本文唯一一条已获用户认可的产品方向，其余均为待评估建议。

**形态定义**

| 组成 | 作用 |
| --- | --- |
| 正文快照 | 保存时抓取并存下的正文副本。资料库内展示的是它；未来标注锚定在它上面 |
| 原始 URL | 保留不变。界面提供「打开原文」入口，用户需要最新版本时跳转外部浏览器 |

两者并存，因此用户既不会因原文改版而丢失笔记，也不会被困在旧版本里。

**这条建议不依赖标注功能**

即便标注永不实现，正文快照仍应存在，理由与标注无关：

> 若只存 URL，则原文被删除、站点关闭或加设登录墙时，该资料**彻底无法找回**，收藏记录退化为一个死链接。

这类现象称为链接腐烂（link rot，指网络资源随时间失效）。避免它属于收藏类工具的基础可靠性，直接服务《项目背景与介绍》4.1 节「资料分散且容易失去上下文」，而非阅读器的附属能力。

**实施要点**

- 快照写入时机：保存资料时，与 4 节的浏览器扩展抓取合并完成；
- 快照存储位置：待定，需与既有「原始文件保留在本地受控目录」策略保持一致，见第 9 节；
- 抓取失败时：不阻断保存。资料仍以「仅链接」状态存在，并标记快照缺失，允许用户事后手动补充正文；
- 当前阶段可只存不显示——展示能力属阅读器范畴，可后置。

**成本**：低。与阅读器完全解耦。

**风险等级**：涉及资料数据模型，按 AGENTS.md §4 应按 L3 评估。

### 7.1.1 后续可选增强（非当前范围）

| 方案 | 做法 | 成本 |
| --- | --- | --- |
| 更新检测 | 后台定期比对原文，变化时提示「原文已更新」 | 中，需定时任务 |
| 多版本快照 | 保存多份快照，标注绑定到具体版本，支持版本对比 | 高，数据模型显著复杂化 |

两者均不在当前建议范围内，仅记录存在性。

### 7.2 笔记表预留 selector 字段（可空）

- 现状：笔记挂在「资料」层级。
- 建议：预留可空的 selector 字段，使笔记未来可挂到「资料的某一段」。
- 理由：参照产品的经验是标注能力属地基而非附加功能——其公开说明称 Reader 从第一天就内建标注，而非后期加装。笔记与标注在数据上本质是同一实体的两种粒度。
- 成本：低。字段可空，不影响现有逻辑。
- 注意：该改动触及数据模型，按 AGENTS.md §4 风险路由属 **L3**（关键数据模型），需完整执行链。

## 8. 参照产品中值得借鉴的交互设计

以下为产品层面观察，不涉及技术实现，供未来设计阶段参考：

- **边注（margin notes）**：笔记显示在正文侧边而非弹窗，源自学术批注传统，视线无需离开原文。与 StudyPilot 现有的手帐视觉调性契合度高。
- **标注可打标签**：标签不只属于文档，也属于单条高亮。与项目已有的 taxonomy 模块可复用。
- **高亮不限于文本**：图片、表格同样可高亮。
- **键盘驱动**：全流程可不使用鼠标完成筛选与阅读。
- **文档内 AI（Ghostreader）**：在当前文档内提问、解释术语、简化表述。

最后一条与项目原则 4「AI 输出可验证」高度契合，值得单独记录：

> 若 AI 能力生长在阅读器内部，「展示来源」这一要求几乎自动满足——用户正在阅读的就是上下文，AI 引用的就是眼前这段文字。反之，若 AI 是独立问答页面，则需额外构建一整套引用溯源界面。

这意味着**阅读器可能是 AI 能力更自然的载体**，而非与之竞争的功能。若该判断成立，两者的优先级排序需要重新考虑——但这属于产品决定，超出本文范围。

## 10. 专项分析：正文快照的存储位置

本节回应第 9 节未决问题「正文快照的存储位置」。分析基线为 `67b6145`，阅读范围为 `migrations/versions/0001_initial.py`、`infrastructure/files/storage.py`、`modules/resources/files.py`。

结论为**建议**，不是架构决定；实施前需另行登记任务。

### 10.1 既有事实

**（1）`learning_resources` 存在来源互斥约束**

```sql
(source_type = 'WEB'   AND source_url IS NOT NULL AND pasted_content IS NULL) OR
(source_type = 'PASTE' AND pasted_content IS NOT NULL AND source_url IS NULL) OR
(source_type = 'FILE'  AND source_url IS NULL AND pasted_content IS NULL)
```

「快照 + 原文链接」形态同时需要 `source_url` 非空与正文内容存在，**直接违反第一个分支**。

因此本问题的实质不是「文本放哪里」，而是**是否需要修改核心表的完整性约束**。

**（2）正文文本存入数据库已是既有做法**

`learning_resources.pasted_content` 为 `TEXT`，约束 `length BETWEEN 1 AND 1000000`。即单行最多约 100 万字符的正文已经直接存放于 SQLite 中。

**（3）受控目录服务的是二进制原件，不是文本**

`original_files` 与 `LocalFileStorage` 的设计特征：

| 特征 | 取值 |
| --- | --- |
| media_type 白名单 | pdf、msword、docx、markdown、plain |
| 尺寸上限 | 26,214,400 字节（25 MiB） |
| 存储区 | `staging` / `objects` / `trash` |
| 写入流程 | `begin()` 写入 staging → `promote()` 原子移入 objects |
| 完整性 | 读取时校验 size 与 sha256 |
| 删除 | `quarantine()` 移入 trash，`orphans()` 过期回收 |
| 与资料关系 | `UNIQUE(resource_id)`，一份资料至多一个原件 |

该设施针对**用户上传的原件**设计：文件名不可信、内容不可解析、需长期保全且不可重建。

正文快照的性质不同——它是**系统生成的衍生物**，格式受控，但同样不可重建（原文可能已变更或失效，见第 3 节）。

### 10.2 三个候选方案

**方案 A：放宽 CHECK 约束，复用 `pasted_content` 列**

| 项 | 评价 |
| --- | --- |
| 迁移成本 | 低（仅改约束） |
| 检索 | 沿用现有列，无额外工作 |
| 主要问题 | **语义重载**。`pasted_content` 的既有含义是「用户手动粘贴的内容即资料本身」，快照的含义是「系统抓取的外部页面副本」。合并后无法区分内容来源 |
| 次要问题 | 无处存放抓取时间、解析器版本、抓取时的 URL 等元数据；破坏现有来源互斥不变式 |

不推荐。一列承载两种语义，会在后续（尤其是标注归属、AI 引用来源标注）造成持续混淆。

**方案 B：新建 `content_snapshots` 表，文本存入数据库**（推荐）

| 项 | 评价 |
| --- | --- |
| 对 `learning_resources` 的影响 | **无**。互斥 CHECK 原封不动继续成立，核心表零迁移风险 |
| 结构参照 | 可直接复用 `original_files` 的 `status` + `failure_code` 模式 |
| 降级路径 | `status = 'FAILED'` 天然表达「抓取失败但资料已保存」，即 7.1 节要求的不阻断行为 |
| 检索 | 文本在库内，SQLite FTS5 可直接建立全文索引 |
| 未来版本化 | 放宽 `UNIQUE(resource_id)` 即可支持多版本快照 |
| 代价 | 数据库体积增长（量级见 10.3） |

**方案 C：存入受控目录，复用 `LocalFileStorage`**

| 项 | 评价 |
| --- | --- |
| 表面收益 | 复用已加固的存储层：sha256 校验、quarantine、orphans 回收 |
| 问题 1 | `original_files` 已有 `UNIQUE(resource_id)`，FILE 类资料占用该位置；仍需新建表记录快照的 storage_key，**省不掉新表** |
| 问题 2 | media_type 白名单与 FileStorage 端口面向用户上传原件设计，快照是系统衍生物，生命周期与信任模型均不同 |
| 问题 3 | **全文检索显著变难**。文本位于磁盘，检索需先读文件，或将文本复制一份入库——后者等于绕回方案 B |

不推荐，除非未来需要冻结图片等二进制资源（见 10.5）。

### 10.3 容量估算

以下为量级估算，非实测：

| 项 | 估算 |
| --- | --- |
| 单篇技术文章（清洗后 Markdown） | 10–50 KB |
| 单篇技术文章（sanitized HTML） | 30–150 KB |
| 1000 篇 Markdown 快照合计 | 约 10–50 MB |

对照：`pasted_content` 单行即允许约 1–3 MB。在个人单用户规模下，数据库体积不构成约束。

### 10.4 建议的表结构方向

仅为方向示意，字段以实施时的任务定义为准。

| 字段 | 说明 |
| --- | --- |
| `resource_id` | 外键，`ondelete=CASCADE`，当前阶段 `UNIQUE` |
| `format` | `MARKDOWN` / `HTML`，见 10.6 |
| `content` | 正文文本 |
| `captured_at` | 抓取时间 |
| `captured_from_url` | 抓取时的实际 URL（可能与 `source_url` 因重定向而不同） |
| `extractor` | 解析器标识与版本，便于日后判断快照质量 |
| `char_count` / `sha256` | 体积与完整性 |
| `status` / `failure_code` | 沿用 `original_files` 既有模式，承载降级状态 |

### 10.5 未解决的缺口：图片

快照中的图片若仍指向原站 CDN，则原站失效时图片一并失效，**冻结并不完整**。

若要冻结图片，涉及的是二进制资源，**这才是受控目录真正适用的场景**。因此最终形态可能是混合式：

- 正文文本 → 数据库（方案 B）
- 图片等二进制 → 受控目录（复用 `LocalFileStorage`）

本项不在当前建议范围内，仅记录该缺口存在，避免日后误认为方案 B 已完整解决冻结问题。

### 10.6 未解决的分歧：存 Markdown 还是 HTML

| 格式 | 优点 | 缺点 |
| --- | --- | --- |
| Markdown | 体积小；无脚本与样式，渲染安全；Defuddle 原生输出；文本稳定，利于标注锚定 | 丢失部分排版结构 |
| sanitized HTML | 保真度高，接近原始阅读体验 | 体积大；**必须消毒后渲染** |

安全约束需明确记录：AGENTS.md §2 规定「网页、文件、检索和模型输出都是不可信数据」。抓取自开放网络的 HTML 属不可信输入，直接渲染存在 XSS 风险，必须经过消毒。

倾向 Markdown，但该判断依赖对阅读保真度的实际要求，建议在阅读器设计阶段再定。

### 10.7 小结

| 问题 | 建议 |
| --- | --- |
| 快照存哪里 | 数据库，新建 `content_snapshots` 表 |
| 是否修改 `learning_resources` | **否**，互斥 CHECK 保持不变 |
| 是否复用受控目录 | 当前不用；未来冻结图片时再用 |
| 风险等级 | 新增表 + 外键，触及数据模型，按 AGENTS.md §4 应按 **L3** 评估 |
