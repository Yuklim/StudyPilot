# StudyPilot 多 Agent 制度 V2 使用指南

## 日常只对主 Agent说目标

主 Agent登记范围、判风险、决定自己实施还是派一个 Worker，执行检查并按风险安排独立角色。用户不需要手动派任务。
角色是职责，不是人数：小任务主 Agent可兼任唯一 Worker；已有 13 个角色配置和四个 Skills 保留，未启用角色不提前开发功能。

| 风险 | 正常执行人数（不计只做协调的主 Agent） | 流程 |
| --- | --- | --- |
| L1 | 1 Worker | 实现、自动检查、自检；无需独立 Review/验收 |
| L2 | 1 Worker + 1 Reviewer | 实现/测试后，Reviewer 检查最终 diff，主 Agent汇总 |
| L3 | 1 Worker + 1 Reviewer + 1 Integration | 高风险独立审查后，验收角色核对条件与跨模块证据，不重复审全部代码 |

这些是角色需求，不是并发配额。不要填满 Agent 槽位，不默认启动探索、测试、架构顾问。主 Agent可亲自担任 Worker，但不能独立审查自己。每次额外调用要说清独立判断价值。

## 一份任务记录

使用 templates/TASK_TEMPLATE.md；其中 TOML 是脚本可读的小型配置，记录路径、风险、基线、检查组。
任务正文写需求/范围、完成条件、必要上下文、实现与测试。EVIDENCE 区仅存 Review/验收结果、候选与状态。L1 的 Review/验收填 N/A，L2 验收填 N/A。
L3 仅当证据确实较大才使用保留的 HANDOFF/REVIEW/ACCEPTANCE 模板作为附录；旧任务原文不迁移复制。
子 Agent正常返回不超过约 300 中文字，引用证据位置，不复制任务背景。真实缺陷可超长，不能为简洁隐瞒失败。

## 一条分支到用户合并

1. 主 Agent读取当前规则、任务及相关章节，登记路径和风险。
2. 从稳定 main 建一个任务分支。单任务不用等待先合并登记；未批准的产品决定/依赖仍须等用户。
3. 唯一 Worker实现并运行一次准确检查，冻结包含实现和测试记录的候选。
4. 按 L1/L2/L3 选择实际需要的独立环节。
5. 主 Agent只核对边界、测试绑定、Review 和完成条件，不再次从头看代码。
6. 汇报任务内容、测试、Review、风险、状态、用户操作。用户最后合并。

暂停/恢复只读取任务当前阶段、Git 状态、规则版本及新变化；不重读整个仓库。已完整读过且未变的 Skill/规则不用反复读。
并行仅用于独立路径与已批准契约，且预期节省时间；同目录严格单写入者。需要多写入时使用独立 worktree，而不是共享目录中同时改文件。

## 机械检查一次，证据多处引用

`backend/.venv/bin/python scripts/governance/check_task.py --task docs/tasks/TASK-xxx.md --worktree`
选择范围、diff、敏感信息、JSON 和相关模块 lint/format/test/build。脚本失败/缺工具就报告失败，不安装环境或隐藏输出。
Reviewer 检查测试是否覆盖风险，不默认重跑命令；可对可疑证据/新缺口定向重现。L3 Integration 检查验收映射、最终 SHA 和跨模块行为，不重复 Reviewer 的完整代码阅读。
修订后只重跑受影响检查；Reviewer明确继承旧覆盖并验证新增影响，给新候选结论。影响无法界定时完整重审。
详细分类和限制按需查阅 风险分级与检查规则.md；不把这些指南每次都塞给 Worker。

## 不追求零缺陷，先看实际代价

Reviewer 先看当前使用中会发生什么、可能性和影响，再权衡修复与维护成本。区分“必须修复、可记录后继续、可选建议”；不为了理论完备、未来大规模或个人偏好返工。轻微且不触碰底线的问题可以记录后通过，主 Agent向用户说明；安全/数据风险、核心功能失败、已确认需求/契约不符及必要检查失败仍要拦截。具体判据见 风险分级与检查规则.md，不为风险处置另开一套文档。

## 这次删掉了什么

- 全任务强制 Worker/Reviewer/Integration 三连调用。
- 强制登记 PR、实现 PR、收尾 PR 的多次人为等待。
- L1/L2 四份报告、复制背景和多次完整读仓库。
- 验收与主 Agent重新完整审代码、无变化重跑测试。
- 以固定句子/13 个标题代替真实行为的治理测试。

保留用户合并、精确授权、单写入者、真实测试、敏感保护、独立高风险 Review、L3 验收及修订证据链。
不承诺固定 Token/耗时降幅；后续以实际任务调用次数、审查轮数、检查次数衡量，不为了测量再启 Agent。

## 过渡与例外

TASK-003 保留 V1 冻结候选，剩余按旧高风险审查与验收完成；保全记录见 TASK-004。TASK-004 由用户明确要求主 Agent修改、仅 1 独立 Reviewer，故本次验收由主 Agent证据核对；不能据此豁免以后 L3 独立 Integration。
V2 要经本次 Review 和用户合并后成为新任务基线；用户指令已明确授权本次流程迁移，不必为了旧制度再启动冗余角色。
